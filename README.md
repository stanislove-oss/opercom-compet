# Оперком: сборка презентации из ноутбука

Ноутбук `main_2.ipynb` строит презентацию по шаблону PowerPoint. Этот репозиторий
добавляет к нему слой, который позволяет запустить ту же сборку **программно** —
одним вызовом, из веб-интерфейса, CLI или планировщика.

Ноутбук остаётся источником правды. Аналитик правит его как раньше; сервис
исполняет ровно те же ячейки, пропуская помеченные тегами.

---

## База: ClickHouse

Проект переехал с MS SQL Server на ClickHouse — так же, как `alpha_compet`
и `chizhik-compet`. База та же, что у чижика: `mediascope_x5_big_v22`.

Куда идти, решает одна настройка. Откат — тоже одна строка, без правки кода:

```bash
DB_ENGINE=clickhouse   # новая база (по умолчанию)
DB_ENGINE=mssql        # прежняя, для сверки и отката
```

Слой доступа — `functions/db.py`: ClickHouse и SQL Server за одним интерфейсом.
Модуль самодостаточный и скопирован из соседних проектов без изменений.

**Запросы переключением движка не меняются и не могут.** У баз разные схемы и
разные диалекты, один и тот же SQL в обеих не выполнится. Поэтому наборов два,
и берутся они **у подключения**, а не по переменной окружения:

```python
db = create_database()          # куда идти — решает DB_ENGINE
Q = queries_for(db.engine)      # чем спрашивать — решает подключение
tv = db.fetch_df(Q.TV_SQL)
```

Иначе в Jupyter выходит ловушка: правишь `.env`, перезапускаешь ячейки, а
модуль лежит в `sys.modules` с прежним выбором. Если наборы всё же разъедутся,
запрос не уйдёт в базу — `_check_dialect` поймает это раньше и скажет, что
перепутано.

### Что изменилось в запросах

| было (SQL Server) | стало (ClickHouse) |
|---|---|
| `media_tv_costs` + 4 `LEFT JOIN` к справочникам | `media_costs_union`, справочники внутри, JOIN-ов нет |
| четыре таблицы затрат | одна, медиа различается колонкой `media_type` (TV/RA/OD/PR) |
| `nat_tv_simple` / `big_tv_simple` / `reg_tv_simple` | `nat_tv` / `big_tv` / `reg_tv` |
| `WHERE prj_name = 'ALL_18+'` | выбор колонки: `` `RtgPer_ALL_18+` `` |
| `SUM(RtgPer_w)` | `` SUM(`RtgPer_w_ALL_18+`) `` — есть только у `reg_tv` |
| `LOWER(...)` | `lowerUTF8(...)` — обычный `LOWER` кириллицу не трогает |
| `UNION` | `UNION ALL` — в ClickHouse `UNION` требует явного `ALL` |
| ключ мёржа собирался руками | `media_key_id` берётся из базы |

**Ловушка регистра.** В базе значения записаны прописными, и ClickHouse регистр
различает: `adTypeName = 'ролик'` вернёт ноль строк и не упадёт. Поэтому везде
`lowerUTF8`. Проверка это демонстрирует на настоящей схеме.

### Две витрины

Затраты и рейтинги берутся из разных баз, и это осознанный выбор:

* затраты в `v22` заканчиваются май'26 — строк за июнь и дальше там нет;
* рейтинги из `v23` брать нельзя: у `reg_tv` там две колонки рейтингов вместо
  пятидесяти двух, и нужного `RtgPer_w_ALL_18+` нет вовсе.

Поэтому база по умолчанию — `v22` (оттуда рейтинги), а таблица затрат
указывается вместе со своей базой: `COST_TABLE=mediascope_x5_big_v23.media_costs_union`.
Замерено в `chizhik-compet` на этой же базе, август 2026.

### Классификация осталась в справочнике

`brand_main`, `advertiser_type`, `category_4/5/7` в базе есть, но отчёт
фильтрует ещё по `competitor` и `include_exclude`, а таких колонок в таблицах
нет — они есть только в представлениях (`reg_tv_weekly_view` и подобные).
Поэтому классификация по-прежнему приходит из Google-таблицы, как в
`alpha_compet`: переезд меняет источник данных, а не цифры отчёта.

Отказаться от справочника можно, но это отдельная задача со сверкой: надо
выяснить, какой `category_N` соответствует `competitor`
(`chizhik-compet/scripts/check_categories.py` читает это из определений
представлений), и решить, чем заменить `include_exclude`.

### Проверка запросов

```bash
python scripts/verify_queries.py     # прогон на встроенном ClickHouse, сервер не нужен
python scripts/check_clickhouse.py --queries app.sql_dict_connection
python scripts/dump_schema.py        # снять схему боевой базы
python scripts/check_filters.py      # насколько режут estat и cleaning_flag
python scripts/compare_engines.py --old mssql --new clickhouse
```

`verify_queries.py` — не линтер: он поднимает настоящий движок ClickHouse
(`chdb`, без сервера), создаёт таблицы **по снятой схеме боевой базы** и
выполняет на них все запросы проекта. Ловятся не только опечатки в SQL, но и
несуществующая колонка и перепутанный регистр имени — ровно как на сервере.
Чего не ловится: данных. Строки-примеры выдуманы, поэтому «ноль строк» здесь
ничего не значит.

Схема боевой базы лежит в `reports/clickhouse_schema.md`.

## Что нужно от вас для интеграции

Веб-интерфейс подключается к пакету `opercom` — HTML/JS здесь нет намеренно.
Минимальная интеграция — четыре вызова:

```python
from opercom.config import load_settings
from opercom.jobs import JobManager
from opercom.preflight import is_ready, run_checks

settings = load_settings()
jobs = JobManager(settings)          # один экземпляр на процесс

# 1. Перед показом кнопки — проверить окружение (можно гасить кнопку).
checks = run_checks(settings)
ready = is_ready(checks)             # checks[i].name / .ok / .blocking / .detail

# 2. Нажатие кнопки: ставим прогон в очередь, сразу отвечаем клиенту.
job = jobs.submit()                  # -> job.id

# 3. Опрос статуса (клиент дёргает раз в 1–2 секунды).
jobs.get(job.id).as_dict(log_offset=already_received_lines)

# 4. Готовый файл.
jobs.get(job.id).output_path         # Path к .pptx, когда status == "succeeded"
```

`job.as_dict()` возвращает:

| поле | смысл |
|---|---|
| `status` | `queued` / `running` / `succeeded` / `failed` / `cancelled` |
| `stage` | текущий раздел ноутбука, например `Слайд 18 нижняя левая таблица` |
| `executed` / `total` / `progress` | прогресс в ячейках и долей 0..1 |
| `log` | хвост лога с `log_offset` (уровни `stage` / `stdout` / `info` / `error`) |
| `error` | при падении: `kind`, `message`, `detail`, `traceback`, номер ячейки |
| `download_available` | можно ли отдавать файл |

Отмена — `jobs.cancel(job.id)`; прогон встанет на границе ближайшей ячейки.

Готовый пример маршрутов лежит в `examples/flask_adapter.py` (~120 строк, Flask).
Это справочник, а не часть продукта — удалите или перепишите под свой фреймворк.

### Ограничения, которые стоит учесть

- **Прогон один за раз.** Раннер делает `chdir`, а сборка упирается в память и
  сетевую шару. `JobManager.active()` возвращает текущий прогон — отдавайте 409,
  а не копите очередь.
- **Состояние в памяти процесса.** При `gunicorn -w N` каждый воркер получит свой
  реестр. Либо один воркер, либо вынести очередь в Celery/RQ, а статус — в Redis;
  интерфейс `JobManager` под такую замену и написан.
- **Отмена — кооперативная.** Зависшая ячейка (долгий SQL-запрос) не прервётся;
  ставьте таймауты на стороне драйвера БД.

## Как размечен ноутбук

У **каждой** code-ячейки есть ровно один тег в `cell.metadata.tags` — том же
месте, что использует Jupyter (`View → Cell Toolbar → Tags`). Умолчания
«без тега = выполняется» нет намеренно: иначе новая исследовательская ячейка
молча уехала бы в боевой прогон.

| тег | что значит |
|---|---|
| `run` | боевая ячейка, выполняется всегда |
| `parameters` | ячейка параметров; рантайм переопределяет её значения |
| `skip` | исследование, `df.head()`, отладка — не выполняется никогда |
| `dev` | служебное (дамп снимков, сверка с baseline) — только при `OPERCOM_RUN_DEV_CELLS=1` |
| `source:db` | загрузка из MySQL + Google Sheets |
| `source:csv` | загрузка из локальных CSV в `dummy_df/` |

`source:db` и `source:csv` — два варианта одного шага. Активен ровно один, по
`OPERCOM_DATA_SOURCE`. Раньше обе ячейки выполнялись подряд и вторая затирала
первую.

Текущий расклад: **148 ячеек к исполнению, 27 пропускается.**

### Что делать при правке ноутбука

1. Добавили ячейку — поставьте ей тег. Забыли — прогон упадёт с явным сообщением.
2. Прогоните проверку:

```bash
python scripts/check_notebook.py                 # боевой вариант
python scripts/check_notebook.py --data-source csv
```

Проверка статическая, ничего не выполняет, и ловит: ячейку без тега,
синтаксическую ошибку, вернувшийся хардкод (`Z:\`, `dummy_df`, имя шаблона),
и имя, которое боевая ячейка читает, но никто из боевых ячеек не определяет —
типичный симптом «ячейку с определением пометили `skip`».

3. Если правили шаблон PowerPoint — сверьте его с ноутбуком:

```bash
python scripts/check_template.py
python scripts/check_template.py --show-unreferenced
```

Ноутбук адресует графики и таблицы по именам объектов (`chart__...`,
`table__...`). Переименовали объект в шаблоне — прогон либо упадёт, либо тихо
не заполнит часть слайдов. Проверка сверяет все 72 ссылки за секунду.

4. Тег можно не проставлять руками — `scripts/tag_notebook.py` предложит его по
   содержимому ячейки (присваивание или импорт → `run`, одно выражение →
   `skip`) и по умолчанию только покажет, что собирается сделать:

```bash
python scripts/tag_notebook.py            # показать предложение
python scripts/tag_notebook.py --apply    # записать
```

## Параметры прогона

Ячейка `parameters` (самая первая) задаёт умолчания для ручного прогона в
Jupyter. При запуске из сервиса `opercom.notebook_runner` переопределяет их
значениями из `opercom/config.py`:

| переменная ноутбука | переменная окружения |
|---|---|
| `TEMPLATE_PPTX` | `OPERCOM_TEMPLATE_PPTX` |
| `OUTPUT_PPTX` | — (свой файл на каждый прогон: `runs/<run_id>/main_2_filled.pptx`) |
| `MMO_DATA_ROOT` | `OPERCOM_MMO_DATA_ROOT` |
| `DIGITAL_DATA_ROOT` | `OPERCOM_DIGITAL_DATA_ROOT` |
| `DUMMY_DF_ROOT` | `OPERCOM_DUMMY_DF_ROOT` |
| `FIVE_DICT` | `OPERCOM_FIVE_DICT_URL` |

Отчётные периоды по-прежнему определяются автоматически из данных
(`functions/define_dates.define_cur_year`) — параметром они не являются.

- **Ячейки 7 и 9/10** — два взаимоисключающих источника данных выполнялись

- **Хардкод путей** (`Z:\...`, `dummy_df/...`, `Х5_Оперком_март_v3_fin_named.pptx`,

- **Файл результата** больше не пишется в корень проекта: каждый прогон получает

- **~22 исследовательские ячейки** (`df.head()`, разовые выборки, повторные

### Что исправлено при переезде на ClickHouse

- **Ключ мёржа со справочником** собирался в трёх местах по-разному:
  `media_type + adId`, `media_type + '_' + adId` и `media_key_id`. Достаточно
  было одного лишнего подчёркивания, чтобы мёрж не нашёл ни одной строки —
  отчёт при этом получался пустым, не падая. Теперь ключ один: `media_key_id`
  из базы, а `normalizer` падает с явным текстом, если мёрж не нашёл ничего.
- **Дедупликация справочника** шла по `adId`, а мёрж — по `media_key_id`.
  `adId` уникален внутри своего медиа, но один и тот же номер встречается и
  в тв, и в наружке, поэтому вторая строка выбрасывалась вместе со своим медиа.
  Теперь схлопывание идёт по тому же ключу, по которому мёрж.
- **`link_dict["media_key_id"].lower()`** в боевой ячейке — у `Series` нет
  метода `.lower()`, нужен `.str.lower()`. Упало бы на первом же прогоне.
- **Имя шаблона** различалось кириллической «Х» и латинской «X» — на вид не
  отличить, а путь не совпадает. `config.py` теперь ищет по точному имени,
  а если не нашёл — по маске `*_named.pptx`.

### Слайды 13-14: почему у duration-графиков нельзя трогать вторую ось

Графики «Ср. хроно бренда» на слайдах 13-14 — комбинированные. В шаблоне у них
**две** оси значений:

| плот | серии | ось значений |
|---|---|---|
| основной, `percentStacked` | `5`, `10`, `15`, `20`, `25`, `''`, `50` | 0..100% |
| служебный, `percentStacked` | `Ср.Хроно` | масштаб из шаблона, например `min=-10`, `max=20` |

Серия `Ср.Хроно` одна в своём плоте, поэтому её столбец всегда равен 100%.
Узкой красной «капсулой» вокруг значения среднего хронометража его делает именно
нестандартный масштаб второй оси: 100% из диапазона −1000%..2000% — это полоска
высотой в треть столбца. Если выровнять эту ось по основной (0..1), капсула
растягивается на всю высоту: подсвечивается не нужная часть столбца, а столбец
целиком.

Поэтому в `update_chart_data`:

- оси служебного плота `Ср.Хроно` исключены из выравнивания масштабов
  (`get_avg_duration_axis_ids` / `get_chart_target_value_axes`) — остальные
  комбо-графики (слайды 21, 22, 24, 30) по-прежнему получают общий масштаб;
- сама серия `Ср.Хроно` не прячется целиком, а оформляется как рамка без
  заливки (`style_avg_duration_marker`), цвет берётся из `color_dict`
  (`'Ср. хроно'`), по умолчанию красный, как в шаблоне.

Инвариант закреплён тестами `tests/test_duration_charts.py` — они гоняют
заливку по реальному шаблону и падают, если масштаб второй оси переписан или
капсула снова стала невидимой.

### На что стоит посмотреть отдельно

- **Ячейка 315** (сверка с `baseline_dataframes.pkl`) содержит
  `len(baseline & dataframes.keys())`, где `baseline` — словарь. Это `TypeError`.
  Помечена `dev`, в боевом прогоне не выполняется.

- **Две таблицы дельт в шаблоне никогда не заполняются.** `fill_delta_tables`
  ищет объект с именем `table__{имя_датафрейма}` и молча пропускает промах.
  Не совпадают:

  | таблица в шаблоне | ближайший датафрейм |
  |---|---|
  | `table__nat_tv_top_brands_labels_ytd` | `nat_tv_top_brands_delta_ytd` |
  | `table__market_top20_media_mix_labels_month` | такого датафрейма нет |

  Первое похоже на расхождение в имени: слайд 6 остаётся без строки дельт.
  Чинится либо переименованием объекта в шаблоне, либо ключа датафрейма — что
  из них канонично, решать вам. `scripts/check_template.py` теперь показывает
  такие расхождения явно.
