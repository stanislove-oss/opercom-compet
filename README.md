# Оперком: сборка презентации из ноутбука

Ноутбук `main_2.ipynb` строит презентацию по шаблону PowerPoint. Этот репозиторий
добавляет к нему слой, который позволяет запустить ту же сборку **программно** —
одним вызовом, из веб-интерфейса, CLI или планировщика.

Ноутбук остаётся источником правды. Аналитик правит его как раньше; сервис
исполняет ровно те же ячейки, пропуская помеченные тегами.

---

## Что нужно от вас для интеграции

Веб-интерфейс подключается к пакету `opercom` — HTML/JS здесь нет намеренно.
Минимальная интеграция — четыре вызова:

```python
from opercom.config import load_settings
from opercom.jobs import JobManager
from opercom.preflight import is_ready, run_checks

settings = load_settings()
jobs = JobManager(settings)          # один экземпляр на процесс

# 1. Перед показом кнопки — проверить окружение (можно гасить кнопку).
checks = run_checks(settings)
ready = is_ready(checks)             # checks[i].name / .ok / .blocking / .detail

# 2. Нажатие кнопки: ставим прогон в очередь, сразу отвечаем клиенту.
job = jobs.submit()                  # -> job.id

# 3. Опрос статуса (клиент дёргает раз в 1–2 секунды).
jobs.get(job.id).as_dict(log_offset=already_received_lines)

# 4. Готовый файл.
jobs.get(job.id).output_path         # Path к .pptx, когда status == "succeeded"
```

`job.as_dict()` возвращает:

| поле | смысл |
|---|---|
| `status` | `queued` / `running` / `succeeded` / `failed` / `cancelled` |
| `stage` | текущий раздел ноутбука, например `Слайд 18 нижняя левая таблица` |
| `executed` / `total` / `progress` | прогресс в ячейках и долей 0..1 |
| `log` | хвост лога с `log_offset` (уровни `stage` / `stdout` / `info` / `error`) |
| `error` | при падении: `kind`, `message`, `detail`, `traceback`, номер ячейки |
| `download_available` | можно ли отдавать файл |

Отмена — `jobs.cancel(job.id)`; прогон встанет на границе ближайшей ячейки.

Готовый пример маршрутов лежит в `examples/flask_adapter.py` (~120 строк, Flask).
Это справочник, а не часть продукта — удалите или перепишите под свой фреймворк.

### Ограничения, которые стоит учесть

- **Прогон один за раз.** Раннер делает `chdir`, а сборка упирается в память и
  сетевую шару. `JobManager.active()` возвращает текущий прогон — отдавайте 409,
  а не копите очередь.
- **Состояние в памяти процесса.** При `gunicorn -w N` каждый воркер получит свой
  реестр. Либо один воркер, либо вынести очередь в Celery/RQ, а статус — в Redis;
  интерфейс `JobManager` под такую замену и написан.
- **Отмена — кооперативная.** Зависшая ячейка (долгий SQL-запрос) не прервётся;
  ставьте таймауты на стороне драйвера БД.

## Как размечен ноутбук

У **каждой** code-ячейки есть ровно один тег в `cell.metadata.tags` — том же
месте, что использует Jupyter (`View → Cell Toolbar → Tags`). Умолчания
«без тега = выполняется» нет намеренно: иначе новая исследовательская ячейка
молча уехала бы в боевой прогон.

| тег | что значит |
|---|---|
| `run` | боевая ячейка, выполняется всегда |
| `parameters` | ячейка параметров; рантайм переопределяет её значения |
| `skip` | исследование, `df.head()`, отладка — не выполняется никогда |
| `dev` | служебное (дамп снимков, сверка с baseline) — только при `OPERCOM_RUN_DEV_CELLS=1` |
| `source:db` | загрузка из MySQL + Google Sheets |
| `source:csv` | загрузка из локальных CSV в `dummy_df/` |

`source:db` и `source:csv` — два варианта одного шага. Активен ровно один, по
`OPERCOM_DATA_SOURCE`. Раньше обе ячейки выполнялись подряд и вторая затирала
первую.

Текущий расклад: **148 ячеек к исполнению, 27 пропускается.**

### Что делать при правке ноутбука

1. Добавили ячейку — поставьте ей тег. Забыли — прогон упадёт с явным сообщением.
2. Прогоните проверку:

```bash
python scripts/check_notebook.py                 # боевой вариант
python scripts/check_notebook.py --data-source csv
```

Проверка статическая, ничего не выполняет, и ловит: ячейку без тега,
синтаксическую ошибку, вернувшийся хардкод (`Z:\`, `dummy_df`, имя шаблона),
и имя, которое боевая ячейка читает, но никто из боевых ячеек не определяет —
типичный симптом «ячейку с определением пометили `skip`».

3. Если правили шаблон PowerPoint — сверьте его с ноутбуком:

```bash
python scripts/check_template.py
python scripts/check_template.py --show-unreferenced
```

Ноутбук адресует графики и таблицы по именам объектов (`chart__...`,
`table__...`). Переименовали объект в шаблоне — прогон либо упадёт, либо тихо
не заполнит часть слайдов. Проверка сверяет все 72 ссылки за секунду.

4. Скрипт `scripts/tag_notebook.py` — первичная разметка. Идемпотентен: повторный
   запуск ничего не портит, а если ноутбук изменился так, что правило устарело,
   честно ругнётся вместо тихой ошибки.

## Параметры прогона

Ячейка `parameters` (самая первая) задаёт умолчания для ручного прогона в
Jupyter. При запуске из сервиса `opercom.notebook_runner` переопределяет их
значениями из `opercom/config.py`:

| переменная ноутбука | переменная окружения |
|---|---|
| `TEMPLATE_PPTX` | `OPERCOM_TEMPLATE_PPTX` |
| `OUTPUT_PPTX` | — (свой файл на каждый прогон: `runs/<run_id>/main_2_filled.pptx`) |
| `MMO_DATA_ROOT` | `OPERCOM_MMO_DATA_ROOT` |
| `DIGITAL_DATA_ROOT` | `OPERCOM_DIGITAL_DATA_ROOT` |
| `DUMMY_DF_ROOT` | `OPERCOM_DUMMY_DF_ROOT` |
| `FIVE_DICT` | `OPERCOM_FIVE_DICT_URL` |

Отчётные периоды по-прежнему определяются автоматически из данных
(`functions/define_dates.define_cur_year`) — параметром они не являются.

## Запуск

```bash
python -m venv .venv && . .venv/bin/activate   # Python >= 3.12
pip install -r requirements-dev.txt
cp .env.example .env                            # заполнить HOST/USER/PASSWORD/DB_NAME

python scripts/build_presentation.py --check    # проверка окружения
python scripts/build_presentation.py --plan     # что будет исполнено
python scripts/build_presentation.py            # боевая сборка
python -m pytest tests/ -q                      # тесты механики (25 шт.)
```

CLI идёт тем же путём, что и кнопка, — им удобно проверять пайплайн до появления
интерфейса и запускать сборку по расписанию.

## Чего не хватает в этом репозитории

Без этого боевой прогон (`OPERCOM_DATA_SOURCE=db`) не поедет — `preflight` проверяет
всё перечисленное и не даст запустить сборку вслепую:

1. **Пакет `app`.** Ноутбук импортирует `app.sql_oop.MySQL` и
   `app.sql_dict_connection` (`TV_SQL`, `OOH_SQL`, `RADIO_SQL`, `PRESS_SQL`,
   `OPERCOM_TV_RATE_NAT`, `OPERCOM_TV_RATE_REG`). В присланном архиве его не было.
2. **`.env`** с credentials оффлайн-базы.
3. **Доступ к сетевой шаре** `Z:\clients\...` — три Excel-файла:
   `top_advertisers_investments_2024*.xlsx`, `top_brands_nattv_2024*.xlsx`,
   `X5_DigitalInvestments_jan'2024*.xlsx`.
4. **`dummy_df/`** — только если нужен режим `OPERCOM_DATA_SOURCE=csv`.

## Что было исправлено в ноутбуке

- **Ячейки 5 и 6** обращались к `tv_norm` / `ooh_norm` до их создания — при
  сквозном прогоне падали. Помечены `skip`.
- **Ячейки 7 и 9/10** — два взаимоисключающих источника данных выполнялись
  подряд, локальные CSV затирали данные из БД. Разведены тегами `source:*`.
- **Хардкод путей** (`Z:\...`, `dummy_df/...`, `Х5_Оперком_март_v3_fin_named.pptx`,
  `main_2_filled.pptx`) вынесен в ячейку параметров.
- **Файл результата** больше не пишется в корень проекта: каждый прогон получает
  свою папку `runs/<run_id>/`, старые чистятся (`OPERCOM_KEEP_RUNS`).
- **~22 исследовательские ячейки** (`df.head()`, разовые выборки, повторные
  просмотры) помечены `skip` и не тратят время прогона.

### На что стоит посмотреть отдельно

- **Ячейка 34** (`cur_month_adex -= 1`) — ручная поправка отчётного месяца.
  Оставлена как есть, поскольку периоды определяются автоматически, но это
  единственное место, где логика зависит от того, когда её последний раз трогали
  руками. Если поправка перестанет быть нужна — её надо снять, сервис её не
  отследит.
- **Ячейка 315** (сверка с `baseline_dataframes.pkl`) содержит
  `len(baseline & dataframes.keys())`, где `baseline` — словарь. Это `TypeError`.
  Помечена `dev`, в боевом прогоне не выполняется.

- **Две таблицы дельт в шаблоне никогда не заполняются.** `fill_delta_tables`
  ищет объект с именем `table__{имя_датафрейма}` и молча пропускает промах.
  Не совпадают:

  | таблица в шаблоне | ближайший датафрейм |
  |---|---|
  | `table__nat_tv_top_brands_labels_ytd` | `nat_tv_top_brands_delta_ytd` |
  | `table__market_top20_media_mix_labels_month` | такого датафрейма нет |

  Первое похоже на расхождение в имени: слайд 6 остаётся без строки дельт.
  Чинится либо переименованием объекта в шаблоне, либо ключа датафрейма — что
  из них канонично, решать вам. `scripts/check_template.py` теперь показывает
  такие расхождения явно.

## Структура

```
main_2.ipynb              размеченный ноутбук — источник правды
functions/                функции построения таблиц и заливки в PowerPoint
templates_pptx/           шаблон презентации

opercom/
  config.py               настройки из окружения
  tags.py                 словарь тегов и отбор ячеек
  notebook_runner.py      исполнение ноутбука по тегам
  preflight.py            проверка готовности окружения
  pipeline.py             один прогон: ноутбук -> .pptx
  jobs.py                 очередь и реестр фоновых прогонов

scripts/
  build_presentation.py   сборка из командной строки
  tag_notebook.py         первичная разметка ноутбука
  check_notebook.py       статическая проверка ноутбука перед деплоем
  check_template.py       сверка ссылок ноутбука с объектами шаблона

examples/flask_adapter.py пример HTTP-контракта (не часть продукта)
tests/                    тесты механики тегов, раннера и очереди
```
